ABSTRACT The use of large language models (LLMs) for generating code in software development
is on the rise. While LLMs demonstrate impressive capabilities, there remains a need to evaluate the
quality of generated code beyond functional correctness. This paper addresses a gap in current research
by evaluating Python code generated by nine state-of-the-art LLMs according to the four main code
quality categories (maintainability, reliability, performance efficiency, and security) defined by the ISO/IEC
5055:2021 standard. The evaluation spans three popular application domains (high-performance computing,
machine learning, and data processing). It employs a stratified prompting approach with varying levels
(short, medium, and long) of detail. Using widely adopted static code analysis tools, the study identifies
which LLMs perform best across these categories. The analysis involved selecting nine algorithms across
three application domains, and the generated code was compared against a human developer using four
static code analysis tools. Metrics were organized into the four ISO 5055 categories, and composite scores
were calculated for each category following preprocessing to ensure accurate evaluation. The results showed
that GPT-4-Turbo produced the most reliable, performance-efficient, and secure code, while Gemini
excelled in generating maintainable Python code among the evaluated models. The study concludes that
properly prompted and configured LLMs can produce code that meets or even exceeds human-developed
code in terms of the four ISO categories. Future work will continue to refine and expand upon these
methodologies on other programming languages.

I. INTRODUCTION

Reports on the enterprise adoption of artificial intelligence
(AI) show that 42% of large IT organizations have actively
deployed AI, with an additional 40% reporting that they
are actively exploring the technology [1]. In particular, specialized large language models (LLMs) for code generation
are increasingly being used to enhance the productivity of
software developers [2].
Existing research evaluating LLMs for coding reveals several prevalent trends, notably a strong emphasis on functional
correctness, which has been a primary focus of current LLM
research [3], [4], [5], [6], [7], [8], [9] and its application in
real-world scenarios [2], [10], [11], [12], [13], [14], [15], [16].
However, concerns have been raised regarding the limited

question is defined as follows: To what extent can LLMs
conform to the four principal categories of ISO 5055? The
study aims to determine which LLMs perform best within
these categories, thereby providing Python developers with
evidence-based insights for selecting models that align with
their software quality requirements.
A. CONTRIBUTION

This research contributes to the ongoing integration of LLMs
in code generation. Through a comprehensive analysis, the
following key findings were identified:
1) Maintainability: Based on the Maintainability Index,
Gemini achieved the highest overall score, closely
followed by GPT-4T. Interestingly, models that
performed poorly in memory usage often exhibited stronger maintainability, suggesting a trade-off
between resource efficiency and structured code
organization.
2) Performance Efficiency and Security: GPT-4T
produced the most reliable and performance-efficient
Python code while also demonstrating superior security
compared to the other eight evaluated models.
3) Prompt Sensitivity: Prompt length significantly influenced code reliability and error rates. However, modelspecific characteristics also played a critical role
in determining overall performance, indicating that
prompt optimization alone cannot ensure consistent
quality.
4) Prompt Design Insights: Medium-length prompts
generally produced more reliable and secure code,
while longer prompts yielded the highest
adherence to Python-specific metrics and coding
conventions.
The above findings not only highlight model-specific
strengths and trade-offs but also offer practical guidance for
developers on selecting and configuring LLMs to generate
high-quality, standards compliant software.

II. BACKGROUND

ISO 5055 is a key standard jointly issued by the International Organization for Standardization (ISO) and the
International Electrotechnical Commission (IEC). It provides comprehensive guidelines for assessing violations of
good architectural and coding practices in source code,
thereby enabling organizations to mitigate operational risks
and reduce associated costs. Advancements in measuring
software structural quality and detecting coding practice
violations through language-specific static analysis tools
have highlighted the need for a more robust and unified
framework [18]. Consequently, ISO 5055 was developed to
address this gap by offering a standardized methodology that
enhances the precision, reliability, and consistency of code
quality evaluation across multiple programming languages
and development contexts.
The standard defines four principal categories for evaluating software quality:
Maintainability: The ability of source code to be
modified efficiently and effectively, allowing developers
to implement changes within a reasonable time frame.
• Performance Efficiency: The extent to which code
utilizes computational resources appropriately; excessive resource consumption can negatively impact other
software processes.
• Reliability: The capability of code to perform consistently under specified and intended conditions, ensuring
that it executes as designed.
• Security: The ability of code to safeguard information
and data from unauthorized access, misuse, or interference by external systems or users.
•

As ISO 5055 is relatively new, only a limited number of
static analysis tools fully support it, particularly for Python.
However, widely used open-source tools can be grouped
according to the ISO 5055 metrics, enabling practical
and automated assessments. Aligning this study with ISO
5055 facilitates the use of such tools to systematically evaluate LLM-generated code across maintainability, performance
efficiency, reliability, and security providing a comprehensive
and standardized assessment of LLMs’ ability to generate
high-quality Python code.
III. RELATED WORK

LLM-based code generation has emerged as a prominent
research area, and the selected studies in this work are
categorized according to the ISO 5055 quality categories.
A. MAINTAINABILITY

Maintainability is the most frequently examined ISO
5055 category in the literature. Molison et al. [23] evaluated GPT-4o-generated Python code of varying difficulty
levels using SonarQube across three model configurations
(i.e., zero-shot, few-shot, and fine-tuned). Their analysis focused on maintainability and reliability, revealing
that LLM-generated code contained fewer bugs overall.

Poldrack et al. [2] reported that GPT-4T effectively simplifies and standardizes source code, improving maintainability through realistic developer interaction simulations.
In contrast, Vaithilingam et al. [15] found that programmers
often struggled to understand and modify generated code,
highlighting usability challenges and maintainability concerns. Similarly, Bubeck et al. [10] observed that GPT-4T
generated code can be difficult to maintain due to frequent
syntactic and semantic errors. Mastropaolo et al. [11]
examined the impact of prompting on code generation with
Codex and found that varying natural language descriptions
produced different outputs in 46% of cases, even when
functional requirements were identical.
Although these studies report both maintainable [2] and
less maintainable [10], [11], [15] LLM-generated code,
none have systematically evaluated maintainability across
all ISO 5055 dimensions, indicating an ongoing gap in
comprehensive code quality assessments.
B. PERFORMANCE EFFICIENCY

Performance efficiency remains one of the most overlooked
categories within ISO 5055. Nascimento et al. [12] found
that while ChatGPT can outperform novice programmers,
it struggles to match the performance of more experienced
developers. Similarly, Huang et al. [3] reported that GPT-4T
generates the most computationally efficient code among
the evaluated models. However, research focused on performance efficiency remains limited and often relies on similar
benchmark-based methodologies [3], [12]. A key threat to
the validity of such studies is the potential inclusion of
LeetCode2 tasks within LLM training datasets. These widely
available problems are frequently used for instruction tuning,
making it plausible that models have been indirectly exposed
to them during training. This overlap underscores the need
for alternative evaluation approaches that assess performance
efficiency on independent and diverse codebases.
C. RELIABILITY

Reliability is another frequently examined ISO 5055 category
in LLM research [2], [10], [11], [15]. A common focus
across these studies is the evaluation of functional correctness using standardized benchmarking datasets. Among
these, HumanEval [8] and the Mostly Basic Programming
Problems (MBPP) benchmark [9] are widely used to assess
language comprehension, algorithmic reasoning, and basic
mathematical capabilities of generated code. However, these
benchmarks suffer from limited test coverage and vague
problem descriptions [5]. Chen et al. [8] identified reliability
limitations in Codex, particularly when handling complex
operation chains. Most existing benchmarks emphasize
function-specific problem descriptions, a limitation that
Du et al. [6] addressed through the introduction of ClassEval,
a benchmark designed for class-level code generation. Their
findings revealed that LLMs perform significantly worse

when generating full class implementations compared to isolated functions. These results, along with prior research [5],
[8], [9], highlight the shortcomings of functionality-focused
benchmarks and raise concerns about the overall reliability
of LLM-generated code. Li et al. [7] proposed an alternative
benchmark for evaluating code review tasks, while Zhong
and Wang [4] introduced a reliability-oriented benchmark
based on 1,208 Stack Overflow programming questions.
Their study revealed recurring patterns of unreliability and
potential security issues across models. Overall, most reliability research remains centered on functional correctness,
which, while useful for model improvement, does not fully
capture real-world software dependability. Schäfer et al. [13]
approached reliability from a more applied perspective,
demonstrating that an adaptive GPT-3.5T-based test generation tool can outperform existing state-of-the-art methods.
Nevertheless, only one identified study explicitly addresses
reliability as a primary research objective, emphasizing
the need for more comprehensive, empirically grounded
evaluations of LLM reliability in realistic development
contexts.
D. SECURITY

Although security is one of the most frequently cited
concerns regarding LLM-generated code, research providing
a thorough evaluation of these issues remains limited.
Licorish et al. [22] compared GPT-4 and human programmers in generating Python software, focusing on code
security and reliability. Their results showed that while
GPT-4 can produce functionally effective solutions, it often
generates more complex code that requires additional reworking to ensure maintainability. Pearce et al. [16] explored
the security implications of Codex by prompting it to
generate code for high-risk cybersecurity scenarios and found
that approximately 40% of the 1,689 programs produced
contained vulnerabilities listed in the Common Weakness
Enumeration (CWE). Similarly, Perry et al. [14] observed
that users with access to LLMs wrote significantly less

IV. METHODOLOGY

Code synthesis has been a long-standing challenge in
computer science [9], [24], [25], [26]. The advent of
attention mechanisms and transformer architectures [27]
enabled scalable sequence prediction and efficient natural
language processing (NLP), forming the foundation of
modern LLMs [25]. Subsequent research demonstrated that
transformer-based LLMs exhibit strong cross-domain capabilities derived from large-scale training data, particularly
excelling in understanding and generating source code [28],
[29]. Consequently, transformer-based and code-specialized
LLMs have become central to contemporary programming
code synthesis research.
Source code analysis provides developers with insights
into potential issues affecting maintainability, performance
efficiency, reliability, and security [30]. Python, being
dynamically typed, presents unique challenges related to
runtime type-checking. To address this, Python organizations
established style and documentation guidelines i.e., Python
Enhancement Proposals, notably PEP 8 and PEP 257 [31].
As these standards are not enforced by default, opensource static analysis tools have been developed to automate
compliance, supporting higher code quality. This study
examines how different LLMs interpret and execute code
generation tasks under varying prompt specificity and
contextual detail. A quantitative methodology is employed to
assess the extent to which LLM-generated code aligns with
ISO/IEC 5055:2021 standards. The overall research process
is illustrated in Figure 1.
A. LLM SELECTION

ISO/IEC 5055:2021 provides a standardized framework for
assessing the internal structure of software with emphasis

on security, reliability, performance efficiency, and maintainability [18]. To evaluate functional correctness in code
generation, benchmarks such as HumanEval [8] and its
popular alternative MBPP [9] are widely used. The EvalPlus
leaderboard served as the primary source for model selection,
offering quantitative assessments of LLM performance across
enhanced versions of these benchmarks, using both individual
and averaged scores.
The benchmark employs the pass@1 metric with greedy
decoding [32], where pass@1 measures the proportion of unit
tests passed by the first generated solution [8], and greedy
decoding iteratively selects the most probable next token [33].
Smaller models, including OpenCodeInterpreterDS (ranked 8) and DeepSeek-Coder-6.7B-Instruct
(ranked 9), were excluded in favour of their larger, betterperforming counterparts. In addition to EvalPlus-listed
models, three widely adopted LLMs such as Codex,
Gemini Pro 1.0, and CodeLLaMA-70B-Instruct
were included to ensure diversity across architectures
and training paradigms. The final selection (GPT-4T,
DeepSeek-Coder, OpenCodeInterpreter, GPT3.5T, WizardCoder, Magicoder, Codex, Gemini,
and CodeLLaMA) thus represents a balanced mix of
top-performing and widely deployed models for a comprehensive comparative evaluation.
B. APPLICATION DOMAIN

Nine representative algorithms spanning three key application domains (such as high-performance computing (HPC),
machine learning (ML), and data processing) were selected
to capture the diversity of real-world software tasks.
1) HPC

The chosen algorithms, Quick Sort (QS), Strassen Matrix
Multiplication (SMM), and Monte Carlo Simulation (MCS),
represent computationally intensive operations. MCS, used
in financial modeling, tests the LLMs’ ability to handle
probabilistic reasoning and large-scale iterations.
2) ML

This domain includes Attention, Convolution, and Principal
Component Analysis (PCA). The Attention mechanism [27]
central to modern NLP and the foundation of LLM
architectures requires managing complex dependencies and
efficient computation. Convolution is fundamental in image
processing and computer vision, emphasizing spatial and
numerical precision, while PCA reduces data dimensionality
by identifying key components explaining the greatest
variance.
3) DATA PROCESSING

Algorithms in this category focus on transforming raw data
into usable forms. The selected algorithms are Huffman Coding (HC) for compression, PageRank (PR) for graph-based
data analysis, and Rabin–Karp (RK) for efficient string

C. PROMPTING

Prompting, the process of designing and refining input
queries to guide LLM outputs, is referred to as prompt
engineering [34]. Common techniques include role-play
prompting [35] and the chain-of-thought method [36],
both aimed at improving reasoning depth and contextual
relevance. To ensure the generalizability of results, this
study adopts a stratified prompting approach classified by
prompt length into short, medium, and long (based on the
methodology proposed by [11]).

1) SHORT PROMPT

Short prompts request the implementation of an algorithm
from scratch with minimal context, relying on the LLM to
infer requirements and apply general coding best practices.
This setup evaluates the model’s ability to abstract and
generalize beyond explicit instructions. However, limited
contextual information may introduce ambiguity, often leading to incomplete or incorrect algorithmic implementations
(see Figure 2).
2) MEDIUM PROMPT

Medium prompts specify functionality, use cases, documentation, and type hints but provide limited details on
argument handling or data types (see Figure 3). This format

encourages the LLM to engage in creative problem-solving
and interpretive reasoning, fostering the generation of more
adaptable and context-aware solutions.
3) LONG PROMPT

Long prompts expand upon medium prompts by adding
explicit instructions for handling edge cases, undefined
arguments, and specific data types (see Figure 4). Designed
to minimize ambiguity, this structure guides the LLM
toward optimal solutions through detailed specification,
thereby testing its ability to process complex, instruction rich
scenarios with precision.
The stratification of prompt lengths serves two primary
research objectives. First, it assesses the adaptability of LLMs
to varying levels of instruction detail, enabling evaluation
across diverse coding scenarios. Second, it provides insights
into model-specific biases, adherence to coding conventions,
and the capacity to exceed prompt constraints in pursuit
of higher-quality solutions. This approach also reflects
the iterative nature of software development, where initial
drafts are refined through successive interactions, allowing
assessment of each model’s consistency and refinement
capability.
If an LLM produced an unsatisfactory output, followup prompts were issued without adding new information
to maintain experimental consistency. All models were
prompted independently, ensuring no contextual carryover
between iterations. While varying prompt lengths naturally
lead to differences in usability and output quality, longer
prompts are generally expected to yield more functionally
complete solutions. Nonetheless, each LLM is expected to
produce code that meets baseline quality standards regardless
of prompt complexity. This stratified design also captures
differences in user intent and developer behavior, illustrating
how prompt specificity influences both performance and
generalization.
D. CODE GENERATION

LLM-generated code was obtained by querying each
model using the prompts defined in IV-C. For GPT-4T
and GPT-3.5T, inference parameters (such as maximum output length and temperature) were available but
kept at default values, except that the maximum length

was increased to prevent premature truncation. Models including OpenCodeInterpreter, WizardCoder,
MagiCoder, and CodeLLaMA lack dedicated graphical
interfaces and were instead executed locally via Ollama,3 a
command-line tool for running LLMs. Codex was accessed
through GitHub Copilot within Visual Studio Code editor,
using its integrated Copilot panel for code generation.
E. BASELINE

A human-developer baseline was established to provide a
consistent benchmark for evaluating how LLMs compare
to human-generated Python code. The baseline solutions
were developed by the first author, who possesses over three
years of professional experience in Python programming and
adheres to standard coding conventions outlined in PEP 8 and
PEP 257. This single-developer baseline was intentionally
chosen to ensure experimental consistency and eliminate
stylistic or methodological variability that could arise from
involving multiple programmers. Each baseline solution
was carefully written to reflect best practices and domain
expertise across all selected application areas. To validate
the selected metrics and ensure a fair comparison, all
developer assistance tools and static analyzers were disabled
during baseline creation. This approach ensures that the
human benchmark provides a controlled, representative, and
unbiased reference for assessing LLM-generated code quality
across four ISO/IEC 5055:2021 categories.

5) NOTE ON WEIGHT SELECTION

Although some metrics may hold greater relevance in specific
contexts, equal weights were assigned across all composite
scores in this study to ensure a consistent and unbiased
evaluation framework. This approach minimizes subjectivity
and enables objective comparison across metrics, thereby
enhancing the generalizability and reproducibility of the
results.
V. DATA CLEANING AND PREPROCESSING

Variations in prompt length and detail can lead to differences
in code output and potential style violations, complicating
direct comparisons. Longer prompts may introduce additional coding errors, thereby skewing the analysis and leading
to biased assessments. To mitigate these effects, preprocessing was applied to normalize results across varying code
lengths, ensuring fairness and comparability. The objective
of this preprocessing step was to provide a clear, contextaware understanding of the data that, when aggregated
with algorithms within the same domain, remains unbiased
toward any specific code sample. Table 3 summarizes the
preprocessing procedures applied to each metric.
A. SMOOTHING

To address zero-counting errors, add-k smoothing was
applied. It is a standard technique used to stabilize sparse data

VIII. NOTE FOR PRACTITIONERS

To translate these findings into practice, this study proposes
a four step guidance to developers and organizations in
selecting and using LLMs effectively. They are model
selection, prompt design, application domain adaptation and
code validation.
A. MODEL SELECTION

For overall high reliability, security, and performance
prefer proprietary models (such as GPT-4T or Gemini).
For projects prioritizing maintainability, transparency,
or local deployment select open-source models (such as
DeepSeek-Coder or CodeLLaMA). For instruction-tuned
adaptability and educational or iterative environments
consider WizardCoder or OpenCodeInterpreter.
B. PROMPT DESIGN

Medium-length prompts that specify structure, documentation, and coding standards achieved the best balance between
code quality and maintainability. Short prompts are suitable
for exploration but may reduce quality, while overly detailed
prompts risk unnecessary code complexity.
C. APPLICATION DOMAIN ADAPTATION

In HPC domains, longer prompts improve handling of
computational and data-intensive tasks. In ML, mediumto-long prompts yield the best balance between accuracy
and efficiency, while in data processing tasks, shorter or
moderately detailed prompts produce cleaner and more
resource-efficient code.
D. VALIDATION AND QUALITY ASSURANCE

Combine static analysis tools (Pylint, Radon, Bandit, and
psutil) with human review to ensure adherence to ISO
5055 categories and minimize the risk of style or logical
inconsistencies.
E. ACTIONABLE TAKEAWAYS

From a practitioner’s perspective, effective integration of
LLMs into software workflows should follow a three-step
process:

IX. LIMITATIONS AND THREATS TO VALIDITY
A. LIMITATIONS

Although the study provides comprehensive quantitative
results across ISO/IEC 5055 categories, the discussion of why
certain models outperform others remains limited because
of restricted transparency and comparability across model
architectures and training corpora. Proprietary LLMs (such
as GPT-4T and Gemini) disclose minimal information
about parameter counts, fine-tuning strategies, or data composition, preventing a detailed causal interpretation of their
superior performance. In contrast, open-source models like
DeepSeek-Coder, CodeLLaMA, and WizardCoder
offer greater methodological transparency but differ significantly in architecture size, instruction-tuning techniques,
and domain coverage. As a result, performance variations
observed in maintainability, reliability, and efficiency could
only be partially attributed to these general factors rather than
empirically validated architectural features.
Consequently, while the findings highlight which models
perform best, a complete interpretive analysis of why they do
so remains constrained by limited public documentation and
methodological opacity inherent to most large-scale LLMs.
This study, while comprehensive, has other limitations as
well:
The selection of LLMs was limited to nine state-ofthe-art models from the EvalPlus benchmark and was
therefore not exhaustive.
• The evaluation focused on real-world programming
challenges to capture diverse contexts in which LLMs
are likely to be applied. However, it may not fully
represent the complex and unpredictable nature of
real-world problems that often involve broader and more
dynamic requirements.
• The analysis centered on ISO 5055, employing widely
used static code analysis tools to assess compliance.
While this method is robust, it may not capture
all nuances of code quality that a human reviewer

model updates could influence reproducibility and reduce the
long-term applicability of the findings.

levels of specificity to reflect diverse real-world development contexts. The results demonstrate that, when properly
prompted and configured, LLMs can produce code that
meets or even exceeds the human developer baseline in
terms of maintainability, reliability, performance efficiency,
and security. Among the evaluated models, GPT-4T and
Gemini achieved marginally superior overall performance.
In future work, the same research methodology could
be applied to compiled programming languages (such as
C, C++, and Fortran) to evaluate the generalizability of
the results and provide a more domain-specific assessment
of performance efficiency. For such analyses, instruction
count during execution could replace CPU usage as a
more precise performance metric. Furthermore, incorporating unit tests to evaluate the intended functionality of the
generated algorithms would offer valuable insights into the
LLMs’ ability to interpret and follow prompt specifications.
Extending this evaluation across different prompt lengths
would also enable a deeper understanding of how prompt
structure influences functional correctness and could guide
the effective integration of LLMs into software development
workflows.
